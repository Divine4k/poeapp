# Map Companion (poeapp): notes for working on it

Electron 33 desktop app for Windows, a second-screen companion for Path of Exile 1. Reads the game log, reads the inventory from screen captures, prices loot via poe.ninja, searches the official trade site, shows a trade overlay on top of the game. User-facing docs: `README.md`. Owner decisions (default keys, where settings live): Project doc `claude/decisions.md`.

## Working rules
- Use the file map below; open only the files the task needs. Do not read README.md unless the task is about it.
- **Pushing to `main` ships the change to every user**: the in-app updater installs the newest commit on `main` (`src/updater.js`). Never push without the owner's click.
- Pushing to the `release` branch builds a new Windows installer (GitHub Actions, `.github/workflows/installer.yml`). Only when asked.
- Bump `version` in `package.json` for user-visible changes.
- When the layout of the code or a command changes, update this file in the same commit.
- A new file must be added with `git add` before committing (`git commit -a` leaves new files out). A required file missing on `main` crashes the app at start, and then the updater cannot fix it: check `git status` before every push.

## Commands
```
npm run t            all tests, short output (~5 s, no Electron needed): one dot per test, failures in full
npm test             all tests, full output (CI uses this)
npm run test:<area>  one area: core, inventory, trade, keys, store, cloud, trouble, tracker, update, jewels, stash
npm start            run the app (needs npm install; Electron)
npm run perf         the speed check (needs npm install; opens a hidden Electron window, ~10 s): times with limits, see "Performance"
node scripts/build-stats.js <stats.ndjson>   rebuild trade-site stat list at a new league
node scripts/build-jewels.js <PathOfBuilding> <skilltree-export>   rebuild the tree and jewel data (new tree)
node scripts/demo-server.js [port] [tables dir]   the main window in a browser with demo data and working Jewels page
```
The whole suite is fast, so `npm run t` after any change is fine. Tests cover `src/core` (stash searches in `test/stashSearch.test.js`; jewels with real slices of the timeless tables in `test/fixtures/timeless.json.gz`), `src/shared.js`, `src/cloud.js`, `src/updater.js`, `src/github.js`, `src/troubleshoot.js`, `src/tracker.js`, `src/ui/keys.js`, `src/ui/steps.js`; `main.js` and the UI pages have no unit tests. For UI changes, the page can be opened in a browser with demo data (`src/ui/index.html`, see demo.js). To boot the real app on Linux: `npm install`, then `xvfb-run -a npx electron --no-sandbox .` with `HOME` set to a temp folder (the network is mostly blocked here; that is fine).

## Roles and troubleshooting
- Roles come from the server (`users.admin` = admin, `users.role` = 'moderator'). `cloud.role` in the app; `canTrouble()` / `isAdmin()` in main.js.
- The sidebar has one **Developer tools** entry (`#nav-dev`, `data-tab="devtools"`) holding two pages switched by the tabs in the top bar (`#dev-bar`, shown on those two pages): Troubleshooting (`#tab-trouble`) and Tracker (`#tab-tracker`, admins only; moderators see no switch). `showTab('devtools')` opens the one last used (`devTab`, localStorage `devTab`; `DEV_TABS` in app/render.js).
- Admins and moderators: the Troubleshooting page (`#tab-trouble`) and the record key (`hotkeys.record`, Shift+F9). Admins: Settings, Developer tools (`#set-dev`): reports repository, GitHub token, every user's role.
- The GitHub token and repository are kept on the server (D1 `meta`, key `github`), handed to admins and moderators when they send. Recordings go to the reports repository, not to this one.
- Admins and moderators also see everyone's recordings: `trouble.syncRemote()` looks in the reports repository once a minute (and when the page opens) and fetches facts and events of new ones; the video is fetched when one is opened (`videoFor`). Removed ones are listed in `recordings/hidden.json` so they are not fetched again.
- Written reports (`kind: 'note'` in meta.json): a note and up to 10 pictures (`image-N.png`), no video. Each one is a problem or a suggestion (`type` in meta.json, chosen before sending; `setType`). Where it stands is one file per recording in the reports repository, `status/<id>.json` = `{ state, type?, by, at }` (`setStatus`, done one at a time): state `''` open, `planned`, `in progress`, `fixed` (shown as Done for a suggestion), `wontfix`; a `type` there overrides the one it was sent with. Older `fixed/<id>.json` files (0.28.2 to 0.45) still count as fixed and move to `status/` with the next change. When you start on what a recording or report describes, set it to `in progress` there; when it is fixed, `fixed`. A recording can be put in the tracker (admins, `troubleTrack` in main.js): attached to a box, or as a new box under one; the box's text gets a line linking `recordings/<id>` (`addRecording`/`removeRecording`, read back as `item.recordings` by `recordingsIn` in src/tracker.js) and the status file keeps `issue: N` (deleting the box clears it; Take out on a box that is already gone just clears it). On the Troubleshooting page that is two buttons: **Make into plan** (a new box, its title, how it starts and which box it goes under) and **Attach to a box**. Boxes show `▶ N`; their dialog lists the recordings with their notes, and Watch plays one with its note (or pictures) in the tracker itself (`tkWatch` in app/tracker.js), with a way on to the Troubleshooting page. Every GitHub request goes out with `cache: 'no-store'` (src/github.js): Chromium otherwise reuses answers for a minute, which made marks undo each other.
- Hook points that feed a recording in main.js: `say`, `push`, the log tail, `applyConfig`, the IPC `action` handler, hotkeys (`noted`), `sendChat`, `showToast`, console output, the window in front. A new thing the app does should call `trouble.event(kind, data)` there too.

## The tracker (the owner's list of ideas and work)
- The Tracker page (`#tab-tracker`, admins only, under Developer tools) shows the GitHub issues of `config.trackerRepo` (default `Divine4k/poeapp`, set in Settings, Developer tools) as a **map** (the default: boxes branching out from one root box for the app, dragged by hand, joined by curves) or a **board** (columns). The map's connections are GitHub **sub-issues** (`setParent` in src/tracker.js; an item without a parent hangs straight under the app); The map shows **one layer at a time**: the box you went into (`tkFocus`, kept in localStorage `trackerFocus`; `'root'` = the app) and what hangs straight under it; a box with items under it has an "N inside" button to go in, the path above the map (`#tk-crumbs`) or Escape goes back up, and new items go into the layer shown. Box positions are `config.trackerLayout`, kept per layer as `"<layer>/<box>"` -> [x, y]; boxes never moved sit in columns of up to 8 right of the layer's box and follow it when it is moved. It uses the GitHub token from the server (the recordings' token), which needs "Issues: read and write" on that repository. main.js: `trackerAction`, IPC `tracker`.
- Where an item stands (`statusOf` in src/tracker.js): closed as completed = Done, closed as not planned = Dropped; open with label `idea` = Idea, `considering` = Considering, `in progress` = In progress, `testing` = Testing, `on hold` = On hold, `blocked` = Blocked (more than one: the furthest along wins); open with none = To do. The board groups them in four columns (Ideas: idea, considering; To do: todo, blocked, on hold; In progress: doing, testing; Done: done, dropped). Priority: label `priority: high` or `priority: low`. Steps: `- [ ]` / `- [x]` lines in the issue text. Other labels are kept as they are.
- Delete (the item dialog) deletes the issue for good through GitHub's GraphQL `deleteIssue` (`deleteItem`); GitHub only allows it with admin rights, so the token needs "Administration: Read and write" on the repository, otherwise the message says so and suggests Dropped.
- **Working from it**: when the owner says "the tracker", "what's next" or names an item (#N), read the open issues of that repository (`gh issue list -R Divine4k/poeapp --state open --json number,title,labels,body`, or the REST API). Read how items hang together from each issue's parent (`GET /repos/<repo>/issues/<n>/parent`, or `parent_issue_url`); a big item's sub-issues are its parts. When you start on one, give it the `in progress` label (and drop `idea` / `considering`); when it is built but not yet checked by the owner, `testing`; tick its steps in the issue text as they get done; put `Closes #N` in the commit message so GitHub moves it to Done once it is on `main`. Something you find that needs doing later becomes a new issue without a status label (To do), made a sub-issue of the item it belongs to. Do not change priorities or move ideas to To do on your own.

## Performance
The app runs beside the game and must stay smooth. Rules for every change (owner's standing wish since 0.43.0):
- **Only the open page is drawn.** `render()` (app/render.js) draws the top bar, toasts and dots, then only the page on screen through `drawPage(name)`; `showTab` calls `drawPage` too, so a page catches up when it is opened. A new page that draws from the state gets its line in `drawPage`, not in `render()`. Nothing is drawn while the window is hidden (`document.hidden`); it redraws when it is back (start.js). What must work in a hidden window (the new-offer sound and dot in `renderTrade`) runs before that check.
- **Write the page with `setHtml(el, html)`** (app/core.js), never a bare `innerHTML` on something drawn from the state: an unchanged box is left alone, so buttons under the mouse keep their click and nothing is parsed again.
- **Nothing heavy per state update, pointer movement, key or timer tick.** No scan of a whole list per row (build a Map once, as `tkIndex` in app/tracker.js); no measuring (`offsetWidth`, `getBoundingClientRect`) inside a loop that also writes; no `new Intl.DateTimeFormat`/`toLocale*String` per row (use `clock`, `dayOf`). Work that follows the pointer runs once per frame (`requestAnimationFrame`, as `tkLinesSoon`).
- **Timers and animation loops stop** when their page is not on screen or the window is hidden (the map clock: `clockStart`/`clockTick` in app/render.js).
- **Main process:** `push()` only asks for an update; calls close together become one (`pushNow`, after `PUSH_WAIT_MS`). Do not push when nothing changed. The state sent to the window holds only what the window reads (`buildState(full)` keeps the long lists for reports). The inventory is not read while another program is in front. No `setBounds` on a see-through window unless the rectangle changed.
- **Measure:** `npm run perf` (scripts/perf.js) times a state update, the Tracker map and a drag against limits, with big preview data. Run it before and after a change that could slow the window and report both numbers. A new heavy page gets its own line there.
- **Kept answers must know when they are stale.** The inventory reader keeps what it worked out per slot and reuses it while the slot's pixels are exactly the same and `index.stamp` is the same (`InventoryReader.look`/`fresh`); every change to the item lists goes through the `IconIndex` methods, which move the stamp. The Items page list (`itemKept` in main.js) and the jewel ranking (`ranked` in core/jewels/timeless.js) work the same way.
- **Files written in the middle of things** (config.json, learned.json, unrecognised.json) go through `writeJsonSoon(name, get)`: a moment later, without blocking, newest value only; `flushSaves()` runs before quitting and restarting. `writeJson` (blocking) is for start-up and quitting.
- Known and not done yet: the state is still sent whole (item icons repeat per map; next step is a revision number per part); the first `archive.list()` reads every saved session file at start; a first inventory reading, or one after the item lists changed, still takes 100-500 ms on the main thread (a worker would fix it); the Wraeclast sidebar embers repaint the sidebar every frame (premium theme, left alone by the owner's wish); stale jewel jobs still queue in the worker.

## Conventions
- Settings: every setting is on the Settings page (`#tab-settings`), bound with `data-cfg="path.in.config"`, saved on change, no Save buttons. Every key goes in `KEY_GROUPS` (src/ui/app/settings.js) only. New config keys get a default in `DEFAULT_CONFIG` (src/config.js).
- Look: colours only through the variables in `:root` (style.css) or `color-mix()` of them, never fixed colours, so every theme works. Panels are one level deep: inside a `.panel`, sections are split by lines, not boxed again. Numbers sit in faint fields, item pictures in `.it` tiles. Rounding: `--r-lg` 14px panels, `--r-md` 10px buttons, `--r-sm` 7px small parts. A new theme: its id in `Theme.STANDARD` or `Theme.PREMIUM` and `Theme.NAMES` (theme.js), its colours and a `.pv-<id>` preview in themes.css. Wraeclast extras go in themes.css under `:root[data-theme=wraeclast]`; broad element rules and lists containing an id use `:where()` so they do not outweigh specific rules. The page allows no inline `style` attributes (CSP); set colours from CSS.
- Messages: `say()` in main.js shows as a small toast at the bottom right; nothing app-wide goes in a banner across the top. Status goes in a chip (`statusChips()` in app/mapping.js): short label, details in its hover text, a click that leads to the fix.
- Restarting (updates) uses `app.relaunch` with `--after-pid`; the new copy waits for the old one (`waitForExit` in leftovers.js). Do not start console programs (cmd, ping, taskkill) without `windowsHide` and no `detached`: each opens a black window.
- UI actions go through `api.action({ type, ... })` to the `actions` table in main.js; main pushes the whole state back (`push()`), the page redraws in `render()` (app/render.js).
- Plain English in user-facing text, no jargon. Comments explain why, in the same plain style.
- Screen captures never see the app's own windows over the game: every overlay window goes through `guard(win)` (src/overlay.js), which sets `setContentProtection` (Windows leaves the window out of captures; OBS and other recorders do not show it either). Only while a troubleshooting recording starts or runs are they shown (`syncCaptureHiding` in main.js). A slot that may be covered by a tooltip and still holds the same item is kept with its last clean picture (`InventoryReader.clean`, `cleanUp`), so map pictures never show a tooltip.
- Nothing is typed into the game without the user's own key press or click (see README "Rules and risk"); keep it that way.
