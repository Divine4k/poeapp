# Map Companion (poeapp): notes for working on it

Electron 33 desktop app for Windows, a second-screen companion for Path of Exile 1. Reads the game log, reads the inventory from screen captures, prices loot via poe.ninja, searches the official trade site, shows a trade overlay on top of the game. User-facing docs: `README.md`. Owner decisions (default keys, where settings live): Project doc `claude/decisions.md`.

## Working rules
- Use the file map below; open only the files the task needs. Do not read README.md unless the task is about it.
- **Pushing to `main` ships the change to every user**: the in-app updater installs the newest commit on `main` (`src/updater.js`). Never push without the owner's click.
- Pushing to the `release` branch builds a new Windows installer (GitHub Actions, `.github/workflows/installer.yml`). Only when asked.
- Bump `version` in `package.json` for user-visible changes.
- When the layout of the code or a command changes, update this file in the same commit.
- A new file must be added with `git add` before committing (`git commit -a` leaves new files out). A required file missing on `main` crashes the app at start, and then the updater cannot fix it: check `git status` before every push.

## Commands
```
npm run t            all tests, short output (~5 s, no Electron needed): one dot per test, failures in full
npm test             all tests, full output (CI uses this)
npm run test:<area>  one area: core, inventory, trade, keys, store, cloud, trouble, tracker, update, jewels, regex
npm start            run the app (needs npm install; Electron)
npm run perf         the speed check (needs npm install; opens a hidden Electron window, ~10 s): times with limits, see "Performance"
node scripts/build-stats.js <stats.ndjson>   rebuild trade-site stat list at a new league
node scripts/build-jewels.js <PathOfBuilding> <skilltree-export>   rebuild the tree and jewel data (new tree)
node scripts/demo-server.js [port] [tables dir]   the main window in a browser with demo data and working Jewels page
```
The whole suite is fast, so `npm run t` after any change is fine. Tests cover `src/core` (stash searches in `test/stashSearch.test.js`; the Regex page's builders and tester in `test/regex.test.js`; jewels with real slices of the timeless tables in `test/fixtures/timeless.json.gz`), `src/shared.js`, `src/cloud.js`, `src/updater.js`, `src/github.js`, `src/troubleshoot.js`, `src/core/diag.js` (`test/diag.test.js`, run with `test:trouble`), `src/tracker.js`, `src/ui/keys.js`, `src/ui/steps.js`; `main.js` and the UI pages have no unit tests. For UI changes, the page can be opened in a browser with demo data (`src/ui/index.html`, see demo.js). To boot the real app on Linux: `npm install`, then `xvfb-run -a npx electron --no-sandbox .` with `HOME` set to a temp folder (the network is mostly blocked here; that is fine).

## Roles and troubleshooting
- Roles come from the server (`users.admin` = admin, `users.role` = 'moderator'). `cloud.role` in the app; `canTrouble()` / `isAdmin()` in main.js.
- The sidebar has one **Developer tools** entry (`#nav-dev`, `data-tab="devtools"`) holding three pages switched by the tabs in the top bar (`#dev-bar`, shown on those pages; `devBar()` in app/render.js): Troubleshooting (`#tab-trouble`), Under the hood (`#tab-hood`) and Tracker (`#tab-tracker`, admins only; moderators do not see its tab). `showTab('devtools')` opens the one last used (`devTab`, localStorage `devTab`; `DEV_TABS` in app/render.js).
- Admins and moderators: the Troubleshooting page (`#tab-trouble`) and the record key (`hotkeys.record`, Shift+F9). Admins: Settings, Developer tools (`#set-dev`): reports repository, GitHub token, every user's role.
- The GitHub token and repository are kept on the server (D1 `meta`, key `github`), handed to admins and moderators when they send. Recordings go to the reports repository, not to this one.
- Admins and moderators also see everyone's recordings: `trouble.syncRemote()` looks in the reports repository once a minute (and when the page opens) and fetches facts and events of new ones; the video is fetched when one is opened (`videoFor`). Removed ones are listed in `recordings/hidden.json` so they are not fetched again.
- Written reports (`kind: 'note'` in meta.json): a note and up to 10 pictures (`image-N.png`), no video. Each one is a problem or a suggestion (`type` in meta.json, chosen before sending; `setType`). Where it stands is one file per recording in the reports repository, `status/<id>.json` = `{ state, type?, by, at }` (`setStatus`, done one at a time): state `''` open, `planned`, `in progress`, `fixed` (shown as Done for a suggestion), `wontfix`; a `type` there overrides the one it was sent with. Older `fixed/<id>.json` files (0.28.2 to 0.45) still count as fixed and move to `status/` with the next change. When you start on what a recording or report describes, set it to `in progress` there; when it is fixed, `fixed`. A recording can be put in the tracker (admins, `troubleTrack` in main.js): attached to a box, or as a new box under one; the box's text gets a line linking `recordings/<id>` (`addRecording`/`removeRecording`, read back as `item.recordings` by `recordingsIn` in src/tracker.js) and the status file keeps `issue: N` (deleting the box clears it; Take out on a box that is already gone just clears it). On the Troubleshooting page that is two buttons: **Make into plan** (a new box, its title, how it starts and which box it goes under) and **Attach to a box**. Boxes show `▶ N`; their dialog lists the recordings with their notes, and Watch plays one with its note (or pictures) in the tracker itself (`tkWatch` in app/tracker.js), with a way on to the Troubleshooting page. Every GitHub request goes out with `cache: 'no-store'` (src/github.js): Chromium otherwise reuses answers for a minute, which made marks undo each other.
- Hook points that feed a recording in main.js: `say`, `push`, the log tail, `applyConfig`, the IPC `action` handler, hotkeys (`noted`), `sendChat`, `showToast`, console output, the window in front, and everything timed (`diag.onTime`, `diag.onSlow`, usage readings). A new thing the app does should call `trouble.event(kind, data)` there too, and be timed (see "Under the hood").

## Under the hood (what the app is doing, in numbers)
Asked for by the owner in 0.51.0, widened in 0.53.0: the app had grown past what he, or Claude, could see into. Always on, for every user (cheap: a few counters); the page is for admins and moderators.
- **Jobs.** Every kind of work is timed under a plain name with a prefix: `state update:`, `inventory:`, `price check:`, `web:` (every `webFetch`, named by `webName`), `file:`, `game log:`, `key:` (each hotkey), `button:` (each `api.action` type), `asked by the window:` (each IPC channel, through `handle` in `setupIpc`), `window:` (what a window measured itself), `start:`. Per job: times, usual (median of the last 200), slow end (95%), worst, last, in all, and how often it went over its limit. Limits go by the start of the name (`LIMITS` in core/diag.js, first match wins; 100 ms otherwise).
- **The start is timed step by step** (0.63): each part of `app.whenReady` in main.js runs inside `step('name', fn)` and shows as `start step: name` (limit 150 ms; `start step: Electron ready` is the time before the app's own code runs). A new thing done at start goes into a step of its own or an existing one, never bare.
- **New work must be timed.** In the main process: `diag.run('prefix: what', fn)` (sync or async), or `const done = diag.start(name); … done(detail)`. In a window: `Hood.run(name, fn)` / `Hood.note(name, ms)`. Pick an existing prefix, or add one with its limit. Work during which the main process does nothing else and that is timed with `start` belongs in `BUSY` (core/diag.js), so a freeze can be put down to it (`run` knows by itself).
- **The rule (owner, 0.53.0): it must hold everything that happens in the app**, so any problem in any part can be read from it afterwards. When you build or change something, ask what Claude would want to know if it went wrong, and record that: time it, give it an outcome, count the ways it can be skipped, and note what it decided. A report that cannot answer "what happened and why" is a bug in this tool.
- **Outcomes.** `done(detail, busy, failed)`: the detail is the outcome in a few words (what came back, how many, why it gave up) and shows as "Last outcome"; `failed` counts it as failed (`run` does both by itself when the work throws). An early `return` that skips work gets `diag.count('prefix: not done, why')`.
- **What happened** (`diag.log`, 4,000 lines): one line per job (quick routine ones under 2 ms are only counted; anything the user set off or that goes to a website always gets its line: `ALWAYS`/`NEVER` in core/diag.js), per freeze and error, and per app event: every `trouble.event(kind, data)` also lands here through `diag.note`, recording or not (hotkeys, buttons, settings, messages, toasts, chat lines typed, the window in front, state changes from `stateBrief`). Never in it: the user's keys and clicks, the game's chat (only log lines the app acted on), and values whose key looks like a token or password (`scrub` in src/troubleshoot.js).
- **Running right now** (`diag.open`): what `start` began and nothing ended; a freeze names these ("in the middle of"), and one that never ends shows on the page.
- **Counts and sizes.** `diag.count(name)` for things worth only a number; `diag.gauge(name, value, unit)` for sizes (first, now, most). `hoodSizes()` in main.js gives the app's own list sizes every half minute, and each window reports its memory and page size: something that only grows shows here. A new long-lived list gets its line in `hoodSizes`.
- **Facts** (`diag.facts`): app and Electron versions, screens, graphics, what the status says, and the settings without private or long parts (`hoodFacts` in main.js).
- **Kept on disk:** `<userData>/diagnostics/this-run.json.gz` every minute and at closing ("closed normally"); at the next start it becomes `the-run-before.json.gz`, so after a crash "Copy the run before" gives what led up to it.
- **Slow moments and freezes.** A job over its limit, and each freeze: the main process (a 250 ms timer that came late by 60 ms or more, with the busy jobs that ended in it and the jobs it was in the middle of) or a window (Chromium's long tasks). The eight longest freezes are kept for the whole run. Every heartbeat's lateness is a job of its own, so the usual smoothness shows too.
- **Usage.** Every 5 s: processor (percent of the whole PC) and memory of each part of the app, and of the PC (the game included). Half an hour is kept. `One state update` (size in KB) is measured every 30 s.
- **The page** (`#tab-hood`, app/hood.js) asks for `api.hood({ op: 'get' })` every 2 s, only while it is on screen (nothing of this is in the state; it gets the latest 400 lines of what happened). `reset` starts the count over, `copy` puts `report()` on the clipboard ("Copy for Claude"), `copyLast` the run before.
- **Send to Claude** (0.61, `sendHood` in main.js, `api.hood({ op: 'send' | 'sendLast', note })`): the same report goes into the reports repository as `hood/<YYYYMMDD-HHMMSS>-<who>[-before]/` with `README.md` (the text, the sender's note on top), `meta.json` and `diagnostics.json.gz`, so reports from the owner and his moderators pile up there. **When the owner says he sent a report (or "check the hood reports"), list `hood/` in the reports repository and read the README of each one newer than the last you read**; say which ones you read by their folder names.
- **Recordings and reports** take it along: `diagnostics.json.gz` (`during` the recording from a `fork()`, and `whole` since the app started; a written report only `whole`), a short `hood` in meta.json (shown on the Troubleshooting page, also for fetched ones), the README's "Under the hood" sections, and on the timeline `timing` (each job of 2 ms or more), `slow`, `freeze` and `usage` events (`timing` and `usage` are counted, not listed, unless Everything is on).
- **Reading one as Claude:** start with the README of the recording (`Under the hood, during the recording`): freezes first, then the jobs table (worst against limit), then slow moments with their times, which line up with the video and the timeline. When the owner pastes a "Copy for Claude" text, it is the same report for the whole run.

## The tracker (the owner's list of ideas and work)
- The Tracker page (`#tab-tracker`, admins only, under Developer tools) shows the GitHub issues of `config.trackerRepo` (default `Divine4k/poeapp`, set in Settings, Developer tools) on **tabs** the owner makes himself (0.55, replacing the one-layer-at-a-time map: he did not want boxes inside boxes). The tabs are listed down the left (`#tk-tabs`, `tkTabsDraw`): Main, then `config.trackerTabs` in order, then any found on boxes; + New tab, double-click (or F2) to rename, drag a tab up or down to reorder it (`tkTabDrag`), × to remove (its boxes go back to Main). A box's tab is its own label `tab: <name>` (`item.tab`; `labelsFor`/`renameTab`/`removeTab` in src/tracker.js), else its parent's tab, else Main (`tkTabOf`, worked out in `tkIndex`). Each tab is shown as a **map** (all its boxes at once, flat, as a tree joined by curves; since 0.60 the tab has no box of its own: the map's left edge is the tab, a rail at `TK_EDGE` with a connector dot where each box straight on the tab joins it and spare dots every 120 px, `data-plug="root"`; dragging from one onto a box puts it straight on the tab, right-clicking one gives the tab's menu) or a **board** (columns, that tab only). Connections are GitHub **sub-issues** (`setParent`); connecting two boxes on a tab keeps both in view; a box whose parent is on another tab hangs straight on its tab (a line from the left edge). Dropping a dragged box on a tab in the list moves it there (`tkSetTab`; to Main while its parent is elsewhere also takes it off that parent). Right-click opens a menu for what is under the pointer (`tkMenuShow`, context in `tkMenu`): a box on the map or board (`tkBoxMenu`: open, add under, take off its line, open on GitHub, copy, status, priority, move to tab, delete), a tab in the list (`tkTabMenu`: open, rename, move up/down, new tab, remove), a line (`tkLineMenu`), a dot on the left edge (the tab's menu, `tkRootMenu`), a board column (add something with that status) and the empty map (add, hide finished, lay this tab out again = `tkRelayout`, refresh). Hide finished (`tkHideDone`, localStorage `trackerHideDone`) leaves Done and Dropped out. The tab shown is kept in localStorage `trackerTab`. Box positions are `config.trackerLayout`, per tab as `"root/<box>"` (Main, as before) or `"tab:<name>/<box>"` -> [x, y]; boxes never moved are laid out as a tree and follow a moved parent. It uses the GitHub token from the server (the recordings' token), which needs "Issues: read and write" on that repository. main.js: `trackerAction`, IPC `tracker`.
- The box window has, besides title, status, priority, tab, part of, notes and steps: **Tags** (the box's own labels, `patch.tags` -> `cleanTags`; offered from every tag in use), **Recordings and reports** (Watch, Take out, + Connect one: a list of sent recordings from `api.troubleList()`, connected through the action `troubleTrack` with `issue`), **Notes over time** (the issue's comments: `listNotes`/`addNote` in src/tracker.js, IPC types `notes`/`addNote`; each with who and when; boxes show `✎ N` from `item.notes`) and **Duplicate** (`tkDuplicate`).
- Where an item stands (`statusOf` in src/tracker.js): closed as completed = Done, closed as not planned = Dropped; open with label `idea` = Idea, `considering` = Considering, `in progress` = In progress, `testing` = Testing, `on hold` = On hold, `blocked` = Blocked (more than one: the furthest along wins); open with none = To do. The board groups them in four columns (Ideas: idea, considering; To do: todo, blocked, on hold; In progress: doing, testing; Done: done, dropped). Priority: label `priority: high` or `priority: low`. Steps: `- [ ]` / `- [x]` lines in the issue text. Other labels are kept as they are.
- Delete (the item dialog) deletes the issue for good through GitHub's GraphQL `deleteIssue` (`deleteItem`); GitHub only allows it with admin rights, so the token needs "Administration: Read and write" on the repository, otherwise the message says so and suggests Dropped.
- **Working from it**: when the owner says "the tracker", "what's next" or names an item (#N), read the open issues of that repository (`gh issue list -R Divine4k/poeapp --state open --json number,title,labels,body`, or the REST API). Read how items hang together from each issue's parent (`GET /repos/<repo>/issues/<n>/parent`, or `parent_issue_url`); a big item's sub-issues are its parts. When you start on one, give it the `in progress` label (and drop `idea` / `considering`); when it is built but not yet checked by the owner, `testing`; tick its steps in the issue text as they get done; put `Closes #N` in the commit message so GitHub moves it to Done once it is on `main`. Something you find that needs doing later becomes a new issue without a status label (To do), made a sub-issue of the item it belongs to (it then shares that item's tab; give a new top-level issue the `tab: <name>` label of the area it belongs to, if the owner has one). Do not change priorities or move ideas to To do on your own.

## Performance
The app runs beside the game and must stay smooth. Rules for every change (owner's standing wish since 0.43.0):
- **Only the open page is drawn.** `render()` (app/render.js) draws the top bar, toasts and dots, then only the page on screen through `drawPage(name)`; `showTab` calls `drawPage` too, so a page catches up when it is opened. A new page that draws from the state gets its line in `drawPage`, not in `render()`. Nothing is drawn while the window is hidden (`document.hidden`); it redraws when it is back (start.js). What must work in a hidden window (the new-offer sound and dot in `renderTrade`) runs before that check.
- **Write the page with `setHtml(el, html)`** (app/core.js), never a bare `innerHTML` on something drawn from the state: an unchanged box is left alone, so buttons under the mouse keep their click and nothing is parsed again.
- **Nothing heavy per state update, pointer movement, key or timer tick.** No scan of a whole list per row (build a Map once, as `tkIndex` in app/tracker.js); no measuring (`offsetWidth`, `getBoundingClientRect`) inside a loop that also writes; no `new Intl.DateTimeFormat`/`toLocale*String` per row (use `clock`, `dayOf`). Work that follows the pointer runs once per frame (`requestAnimationFrame`, as `tkLinesSoon`).
- **Timers and animation loops stop** when their page is not on screen or the window is hidden (the map clock: `clockStart`/`clockTick` in app/render.js).
- **Main process:** `push()` only asks for an update; calls close together become one (`pushNow`, after `PUSH_WAIT_MS`). Do not push when nothing changed. The state sent to the window holds only what the window reads (`buildState(full)` keeps the long lists for reports). The inventory is not read while another program is in front. No `setBounds` on a see-through window unless the rectangle changed.
- **Measure on the owner's PC:** the Under the hood page shows what every job really takes there; ask for its "Copy for Claude" text, or a recording, before guessing at a slowdown.
- **Measure:** `npm run perf` (scripts/perf.js) times a state update, the Tracker map and a drag against limits, with big preview data. Run it before and after a change that could slow the window and report both numbers. A new heavy page gets its own line there.
- **Kept answers must know when they are stale.** The inventory reader keeps what it worked out per slot and reuses it while the slot's pixels are exactly the same and `index.stamp` is the same (`InventoryReader.look`/`fresh`); every change to the item lists goes through the `IconIndex` methods, which move the stamp. The Items page list (`itemKept` in main.js) and the jewel ranking (`ranked` in core/jewels/timeless.js) work the same way.
- **Files written in the middle of things** (config.json, learned.json, unrecognised.json) go through `writeJsonSoon(name, get)`: a moment later, without blocking, newest value only; `flushSaves()` runs before quitting and restarting. `writeJson` (blocking) is for start-up and quitting.
- **Screen capture, the quick way (0.63).** Electron's own capture (`desktopCapturer`) makes full-size pictures of every screen in the main process: about half a second frozen per inventory reading on the owner's PC. `captureFrame` (src/capture.js) therefore asks a helper process (src/capturehelper.js: PowerShell with a few lines of C#, a plain copy of the one screen's pixels) once that helper is **trusted**: in every run it starts on trial, and for readings with the inventory open both pictures are taken and the 60 slots compared byte for byte (`judge`, called from `readInventory`; `slotsSame`). Three matching readings in a row (56 of 60 slots or more, a tooltip may move in between) and it is used; two that differ, a helper that does not start or answer, or a screen whose real rectangle is not known, and the app stays the old way for that run. Once trusted, every 30th picture is taken both ways and compared again (two that differ and it goes back to the old way), and a picture of one colour from corner to corner is thrown away. With one of the app's own windows showing over the game the old way is used as well (it leaves them out; whether the copy does is not known). The fact "Screen capture" and the notes of kind `capture` in Under the hood say which way is in use and why. **Reading loot is only as good as its pixels (owner, 2026-11-26): never loosen this comparison, and never feed the reader pixels that were not shown to be the same.**
- Known and not done yet: the state is still sent whole (item icons repeat per map; next step is a revision number per part); the first `archive.list()` reads every saved session file at start; a first inventory reading, or one after the item lists changed, still takes 100-500 ms on the main thread (a worker would fix it); the Wraeclast sidebar embers repaint the sidebar every frame (premium theme, left alone by the owner's wish); stale jewel jobs still queue in the worker.

## Conventions
- Settings: every setting is on the Settings page (`#tab-settings`), bound with `data-cfg="path.in.config"`, saved on change, no Save buttons. Every key goes in `KEY_GROUPS` (src/ui/app/settings.js) only. New config keys get a default in `DEFAULT_CONFIG` (src/config.js).
- Look: colours only through the variables in `:root` (style.css) or `color-mix()` of them, never fixed colours, so every theme works. Panels are one level deep: inside a `.panel`, sections are split by lines, not boxed again. Numbers sit in faint fields, item pictures in `.it` tiles. Rounding: `--r-lg` 14px panels, `--r-md` 10px buttons, `--r-sm` 7px small parts. A new theme: its id in `Theme.STANDARD` or `Theme.PREMIUM` and `Theme.NAMES` (theme.js), its colours and a `.pv-<id>` preview in themes.css. Wraeclast extras go in themes.css under `:root[data-theme=wraeclast]`; broad element rules and lists containing an id use `:where()` so they do not outweigh specific rules. The page allows no inline `style` attributes (CSP); set colours from CSS.
- Messages: `say()` in main.js shows as a small toast at the bottom right; nothing app-wide goes in a banner across the top. Status goes in a chip (`statusChips()` in app/mapping.js): short label, details in its hover text, a click that leads to the fix.
- Restarting (updates) uses `app.relaunch` with `--after-pid`; the new copy waits for the old one (`waitForExit` in leftovers.js). Do not start console programs (cmd, ping, taskkill) without `windowsHide` and no `detached`: each opens a black window.
- UI actions go through `api.action({ type, ... })` to the `actions` table in main.js; main pushes the whole state back (`push()`), the page redraws in `render()` (app/render.js).
- Never `window.confirm`, `window.alert` or `window.prompt` in a window: after one, Electron on Windows can leave text fields unable to take typing until the window loses focus and gets it back (the owner hit this in 0.55). Ask with `await askYes(text, { yes, no, danger })` and tell with `await tell(text)` (app/core.js, `#ask-dialog`).
- Plain English in user-facing text, no jargon. Comments explain why, in the same plain style.
- Screen captures never see the app's own windows over the game: every overlay window goes through `guard(win)` (src/overlay.js), which sets `setContentProtection` (Windows leaves the window out of captures; OBS and other recorders do not show it either). Only while a troubleshooting recording starts or runs are they shown (`syncCaptureHiding` in main.js). Covered slots are found, not guessed: `coveredCells` (core/inventory/grid.js) marks slots whose grid lines are dark (a tooltip's box), and `unsureSlots` (reader.js) adds the slots under the mouse pointer. A covered slot keeps what was known (no matching); one under a tooltip's dark box that was never known is not matched either (status `covered`: a near-black picture was read as Scarecrow's Pitchfork), and one that still holds the same item keeps its last clean picture (`InventoryReader.clean`, `cleanUp`), so map pictures never show a tooltip. After a reading with covered slots, up to 6 more follow within 3 s while the mouse moves (`followUp`, `FOLLOW` in main.js), until one has nothing covered. Back from a map, covered slots never seen clearly (`result.blind`) are tracked (`trackBlind`); when follow-ups end with some left, one in-game hint asks to move the mouse (`tellBlind`), and one found empty before it was seen is noted per map (`session.addHidden`, `uncounted.hidden`). Each reading's capture and reading time goes into troubleshooting recordings (`inventoryRead` event). The map inventories (`invGridHtml`, `snapHtml` in app/mapping.js) draw recognised slots from what was read (item icon from `run-snapshot`, number); unrecognised and doubtful slots show the picture taken. The Photo button (`invPhoto`, kept per window in localStorage) shows the pictures as taken. Back from a map, slots filled from the stash (first seen empty, or holding something else, in `ledger.arrival`) are left out of the map's picture, and a picture that shows one is replaced even by a smaller one (`keepSnapshot`). A trip that brought nothing new (every slot taken in with you, `nothingNew`) shows one line in place of its picture, with Show picture (`openTrips`). Taken-in slots are greyed, darkened and striped with a dashed frame (`.carried`), never only dimmed.
- Nothing is typed into the game without the user's own key press or click (see README "Rules and risk"); keep it that way.
